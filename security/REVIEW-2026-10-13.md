## Verification performed

- **135 automated tests passed**, including existing rendering, XSS, Edge Function authorization/input validation, clean routes, navigation, themes, motion, and optional newsletter sections, plus new archive, recovery, admin-session, and publishing regression cases. The original visual release passed 134; a follow-up added a runtime dependency audit guard. These run in Node with a DOM simulation; they are not browser screenshots or device tests.
- **10 live read-only database checks passed** using `tests/database-readonly-security.sql`: anonymous/nonmember restrictions on memberships, hidden announcements, unpublished newsletters, and author identifiers; public service availability; forged metadata role rejected; authenticated clients lack direct membership mutation grants. The transaction was read-only and rolled back. No private user data was retrieved. Visibility checks without fixture insertion are complemented by inspection of the active policies.
- RLS was enabled on all four public application tables. Content writes require membership in `admin_users`; public newsletter policies require published status and a publication timestamp. No public Storage buckets were found.
- The deployed `admin-users` function (version 4) matched the repository source. Its gateway `verify_jwt: false` is paired with the function's `withSupabase({auth: "user"})` authentication middleware and a server-side Owner membership check; this is not an unauthenticated admin endpoint.
- `npm audit`: **0 reported vulnerabilities** in the repository dependency graph. A separate lockfile audit of `@supabase/supabase-js@2.112.2` and `@supabase/server@1.9.1` and their resolved npm dependencies also reported **0**. The audit-only manifest and lockfile are now committed under `security/runtime-dependencies/`; CI audits both graphs and a test prevents the manifest from drifting from the source package pins. This is an advisory-database check, not proof that packages contain no defects or an attestation of all deployed transitive versions.
- The four application helper functions deny direct execution by `anon` and `authenticated`. Their fixed search paths and the enabled last-owner/audit triggers were inspected. The deployed last-owner guard uses a transaction advisory lock when demoting or deleting an owner.
- Seven HTML pages checked: **73 local asset references resolved**, no duplicate IDs or broken static in-page anchors. **163 translation references** had English and Spanish strings. All **nine CSS files parsed**, browser JavaScript syntax checks and `git diff --check` passed.
- Reviewed light/dark color pairs and corrected low-contrast admin record IDs and theme gaps. Primary body/muted/button color pairs checked exceed 4.5:1 on their specified solid backgrounds; this is not a full rendered WCAG audit of translucent compositing.
- A targeted source scan found no matches for common private-key, GitHub-token, AWS-access-key, or JWT credential patterns. The browser Supabase publishable key is intentionally public and does not replace database authorization.

## Open security work

1. **Leaked-password protection is disabled.** The current Supabase security advisor returned this warning. Enable it in the project's authentication/password settings and verify the resulting sign-in/password-change behavior. The connected tools do not expose this setting. [Supabase remediation](https://supabase.com/docs/guides/auth/password-security#password-strength-and-leaked-password-protection).
2. **Administrator MFA remains unenrolled and unenforced.** The aggregate query found zero verified MFA factors. Add enrollment, challenge, and recovery UI; enroll at least the owner; then enforce AAL2 for CMS mutations and the Owner function. Enforcing it immediately would lock existing administrators out. [Supabase MFA guidance](https://supabase.com/docs/guides/auth/auth-mfa).
3. **Hosting response headers still need a separate rollout.** The October 10 audit documented missing anti-framing and other hosting headers. Draft PR [#14](https://github.com/ministerioshekinah/church-hub/pull/14) prepares an alternate hosting configuration; it was not merged or activated here. `frame-src 'none'` blocks frames embedded by this site; it does **not** prevent another site from framing this site. `frame-ancestors` must be delivered as an HTTP header. DNS/proxy/hosting access and a deployment check are still needed.
4. **Public signup configuration needs a current check.** The October 10 review reported public signup enabled. The site has no public registration feature, so invitation-only registration is preferable. This setting was not revalidated or changed in this session. RLS membership checks remain the content authorization boundary.

## Limits and release safeguards

Live browser access to the website was declined by the session's permission control. No alternate browser or direct HTTP path was used to bypass that decision. Consequently, this review does not claim a rendered desktop/mobile/Safari check, measured animation frame rate, current production HTTP-header verification, or authenticated end-to-end testing against real accounts. Existing live content was not edited as a test.

The changes are submitted through a GitHub pull request with the existing Frontend and Security Checks workflow. GitHub Pages deployment status can confirm publication, but cannot substitute for a browser visual check. The checks above found no failures in their tested scope; they cannot guarantee that a website has no exploitable vulnerabilities.

Rollback: revert the refinement pull request through GitHub. The pre-change main commit is `ed44f393166191f4880a747def2a5f303e4d6d31`. There are no accompanying database migrations to reverse.

## Reproduce

```sh
npm ci --ignore-scripts
npm test
npm run security:test
npm audit --audit-level=high
npm audit --prefix security/runtime-dependencies --audit-level=high
```

The read-only SQL file is intended for a trusted SQL administrator in the intended project. It does not install fixtures or change production data. The older `security:live` script also sends live website HTTP requests; run that only when access is permitted. It was not run during this review.
