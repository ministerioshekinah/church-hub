## Remaining protections to add

| ID | Priority | Finding | Next step |
| --- | --- | --- | --- |
| F01 | High priority hardening | Administrator MFA is not enrolled or enforced | Implement the enrollment and challenge flows, enroll the owner, and enforce MFA for privileged access in both RLS and the Edge handler. Do not enforce aal2 before a working enrollment/recovery path exists. |
| F02 | Recommended | Leaked-password protection is disabled | Enable leaked-password protection if supported by the project plan and choose a strong, unique administrator password. |
| F03 | Recommended | Public account signup remains enabled | Disable new public signups while preserving the owner invitation flow. |
| F04 | Recommended | Administrator page lacks a framing restriction | Configure an appropriate frame-ancestors policy at a hosting or proxy layer that supports response headers; a meta CSP cannot enforce this directive. |
| F05 | Defense in depth | Strict-Transport-Security header is absent | Configure HSTS through a suitable host/proxy after validating HTTPS coverage. Do not blindly enable includeSubDomains or preload. |
| F06 | Defense in depth | X-Content-Type-Options header is absent | Set X-Content-Type-Options: nosniff through a host/proxy with response-header support. |

**MFA is the highest-priority follow-up.** Enrollment alone is insufficient: the application also needs a working challenge flow and server-side enforcement. The current checks verify the existing administrator allowlist; they do not establish MFA protection. See [Supabase MFA guidance](https://supabase.com/docs/guides/auth/auth-mfa).

Supabase Security Advisor returned one warning: [leaked-password protection is disabled](https://supabase.com/docs/guides/auth/password-security#password-strength-and-leaked-password-protection). It returned no other security advisories during this run. Public signup remains enabled, but the tested database policies still block accounts outside the administrator allowlist.

Header findings are based on the live administrator page’s response. A meta CSP cannot replace an HTTP `frame-ancestors` policy. Address these through hosting/proxy configuration; this review did not change hosting or authentication settings.

## Safety and limits of this run

The database tests ran in an explicit transaction ending in `ROLLBACK`, with local lock and statement timeouts. No Auth accounts or invitations were created. Live HTTP probes requested only public content or operations expected to be denied; they did not publish, edit, or remove church content.

The handler tests mock the authentication wrapper and data-provider responses. Live probes independently rejected missing, malformed, and forged sessions. A real authenticated owner browser session, browser attack simulation, denial-of-service testing, and brute-force testing were outside scope. Package advisories and pattern scans cannot find every unknown vulnerability or secret type.

The Supabase function uses SDK user authentication; its legacy gateway `verify_jwt=false` setting is intentional and is not evidence of unauthenticated access. The source requires user authentication and checks owner membership, and live invalid-token requests returned 401.
